# 安全公告与漏洞处理流程（P6-003）

依据：`third-party-plugin-ecosystem-rfc.md` §13.4（SEC 测试表——本流程的定级锚）、§14（威胁模型）、§11.3（撤销机制）；`scripts/tests/plugin-sec-coverage.cjs`（SEC 覆盖矩阵）；`docs/plugin-security.md`（面向开发者的安全模型说明，本文档是其**流程侧**补充）；`EXECUTION_PLAN.md` P6-003。
放置说明：RFC §19.1 明文预留 `rfcs/plugin-security-rfc.md` 作为安全专项文档位。受众 = 维护者（执行流程）+ 安全研究者（报告入口与披露政策），治理属性强于教程属性，故落 `rfcs/` 根目录而非 docs/ 八篇开发者文档白名单（P0-004 口径不动）。

## 0. 目标与适用范围

定义 LexiNote 插件生态安全漏洞的**接收 → 定级 → 修复 → 公告**全流程。适用对象：

- 宿主插件运行时（沙箱/权限/RPC/安装链）中的漏洞；
- 第三方插件的恶意行为或安全缺陷（对应 RFC §11.3 撤销机制）；
- 供应链事件（包篡改/元数据回滚/密钥泄露，SEC-014..017 族）。

不适用：宿主非插件面的一般性 bug（走普通 issue 流）；未触发安全语义的性能问题。

## 1. 报告入口（intake）

| 渠道 | 用途 | 现状 |
|---|---|---|
| GitHub 私有安全通告（Security Advisory / 私密 issue） | 首选：默认保密，不进公开 issue 流 | 待公开仓启用时开放（发布动作本身受 ADR-015/B-003 纪律约束，见第 5 节） |
| 维护者邮箱 | 备用通道；收到后 48h 内转录为私有通告编号 | 通道地址随公开仓启用一并公布 |

纪律：**公开 issue/聊天渠道收到安全报告时，受理人第一动作是请求转入私密通道并限制转发**，未确认前不在公开面复现细节。

## 2. 受理与保密（embargo）

1. **确认**：48 小时内确认收到，指派编号 `LEXINOTE-SEC-<年>-<序号>`（模板见第 7 节）。
2. **保密期（embargo）默认 90 天**：自报告日起，细节仅在修复所需的最小范围（维护者 + 报告者）内流转。
3. **提前披露**：存在活跃利用证据 → 不再等 90 天，修复就绪即走第 5 节发布；90 天到期仍未修复 → 按协调披露惯例发布通告（含未修复风险与缓解措施），不无限期扣押。
4. **延长**：仅经报告者书面同意，且须在通告时间线中如实记录。

## 3. 定级（triage）

### 3.1 严重级档位（CVSS 风格四档）

| 档位 | CVSS 式分值区间 | 判据 |
|---|---|---|
| Critical | 9.0–10.0 | 沙箱逃逸/宿主对象可达/凭据获取/任意代码执行；签名与信任链被击穿（可批量投毒） |
| High | 7.0–8.9 | 越权读写用户数据（Vault/跨插件存储/命令）；身份伪造；代理绕过 |
| Medium | 4.0–6.9 | 资源耗尽/挂起类可用性打击；卸载残留；降级防御绕过 |
| Low | 0.1–3.9 | 边缘信息泄露面、需要非常规前置条件的弱化 |

### 3.2 SEC 编号映射（定级锚）

triage 必须把漏洞映射到 RFC §13.4 的 SEC-001..018 场景族（同一编号体系由 `plugin-sec-coverage.cjs` 机器对账），默认档位如下（实际定级可上下调整，但须在通告中写明调整理由与命中场景编号）：

| 默认档位 | SEC 场景族 |
|---|---|
| Critical | SEC-001（父窗口 DOM）、SEC-002（宿主全局对象）、SEC-004（Session Token）；SEC-014/015/017（签名篡改/元数据回滚/密钥撤销失效——信任链级） |
| High | SEC-003（跨插件 iframe）、SEC-005（伪造 pluginId）、SEC-006（跨插件存储）、SEC-007（跨插件命令删除）、SEC-008（未授权 Vault 写）、SEC-009（路径穿越）、SEC-010（未授权网络） |
| Medium | SEC-011（大请求资源耗尽）、SEC-012（RPC 超时滥用）、SEC-013（卸载残留）、SEC-016（版本降级绕过） |
| Low | SEC-018 的低危内容变体（恶意依赖/包内容按实际可达性上浮，可达即 High/Critical） |

## 4. 修复流程

1. **修复分支与回归用例**：修复必须同轮补行为级正/负用例——落在 §3.2 命中的既有门禁（如 authz-matrix/context-isolation/net-request-url 等），并在 `plugin-sec-coverage.cjs` 矩阵更新该 SEC 条目的 needle（用例改名/漂移即矩阵红，P1-009 机制）。
2. **全量门禁**：`release-gate --ci` 全绿 + `hvigorw assembleHap` 构建绿是修复合入的最低标准。
3. **版本与分发**：修复随 API 版本规则（见 `plugin-api-evolution-rfc.md` 第 2 节）递增版本；发布走 RFC §8 安装包/签名/哈希链（B-002 未闭环期间，修复以宿主应用更新形式交付，市场链修复需 P5-002/003 就位）。
4. **撤销联动**：判定为 Critical 且涉恶意插件 → 触发 RFC §11.3 撤销链（禁装/禁更新/已装提示/按风险停用/吊销密钥/审计记录/不自动删数据）；撤销条目经 revocations 数据源下发（P5-003 接线就位前：撤销先入发布仓索引元数据，宿主侧消费随 P5-002 闭环）。

## 5. 公告发布流程（人工门）

发布顺序：修复可用（或 embargo 到期）→ 公告定稿（第 7 节模板）→ **人工发布授权**。

- **发布是人工门**：公告的 git push、GitHub Advisory 发布、市场公告等一切对外可见动作由维护者**人工执行**。任何代理/自动化工具不得自动推送（与工程纪律"不可逆 git 操作一律先请示"、B-003 发布决策一致）；代理可以起草、对账、预演（dry-run），落盘的只是待发布稿件。
- 发布渠道：GitHub Security Advisory（主）+ 发布仓通告条目（`lexinote-releases`，随 ADR-015 开放）+ `docs/plugin-security.md` 的"已处置安全事件"节摘要。
- 发布内容脱敏红线：不包含可复现的利用代码细节（除非活跃利用迫使其公开）、不包含其他用户的任何数据、不包含内部工程记录中未公开的路径。
- 报告者致谢在发布稿中确认（报告者可要求匿名，模板含该字段）。

## 6. 紧急响应（活跃利用）

确认活跃利用时：立即走撤销链（§4.4）→ 宿主侧 fail-closed 开关（如沙箱轨/legacy 轨停用开关先例）评估是否需要紧急默认翻转（ADR 复审程序）→ 修复+公告提前发布（§2.3）→ 事件复盘记入 PROGRESS。

## 7. 安全公告模板（SEC advisory template）

发布稿按本模板填写（字段缺项写 `N/A` 并注明原因，不许留空）：

```markdown
# LEXINOTE-SEC-<年>-<序号>：<标题>

- 状态: draft | reviewed | published | withdrawn
- 严重级: Critical | High | Medium | Low（CVSS 式分值: <0.1–10.0>，定级理由见下）
- 命中 SEC 场景: SEC-<编号>(<场景名>)（RFC §13.4 映射，见 rfcs/plugin-security-rfc.md §3.2）
- 受影响组件: <模块/文件面>
- 受影响版本: <= <版本>（修复版本: >= <版本>）
- 报告来源: <报告者/渠道>；致谢: <姓名或"应要求匿名">
- 描述: <漏洞是什么，非敏感表述>
- 影响: <攻击者能做什么，前置条件是什么>
- 利用状态: 无已知利用 | 有 PoC（保密期内不公开）| 活跃利用
- 缓解措施（升级前临时方案）: <关闭某开关/撤销某插件/…>
- 修复说明: <修复方式一句话 + 回归用例落在哪个门禁>
- 时间线:
  - 报告日: <YYYY-MM-DD>
  - 确认/定级日: <YYYY-MM-DD>
  - 修复合入日: <YYYY-MM-DD>
  - 公告发布日: <YYYY-MM-DD>（embargo: 90 天默认，起算自报告日）
- 参考资料: <相关 ADR/RFC 节/门禁名>
```
